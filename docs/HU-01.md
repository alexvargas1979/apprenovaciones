# HU-01 · Conservación de propiedades y presupuestos

La ampliación conserva `properties` y `settings` sin cambiar sus datos. El ID de la propiedad identifica el expediente inicial en `investment_projects`. El presupuesto y su cálculo continúan usando el formato anterior durante esta etapa.

## Implementación

- Drizzle 0002 agrega tablas sin modificar ni eliminar tablas previas.
- Un POST autenticado procesa hasta 20 propiedades pendientes del usuario por llamada. El cliente reanuda hasta terminar antes de cargar la lista.
- Cada propiedad se procesa en un lote atómico: copia exacta de payload y fecha anterior, saldos iniciales de importes manuales y registro del expediente. Conflictos de clave no duplican datos.
- PUT también preserva la propiedad anterior antes de su primera edición, para cubrir clientes abiertos antes del despliegue.
- Propiedades nuevas se registran como nuevas en la misma transacción que su creación; no se presentan como migraciones históricas.
- Los acumulados manuales se conservan como texto numérico en el respaldo de saldos para evitar forzar redondeo de importes originales. Se incluyen ceros explícitos y partidas desactivadas; no se generan facturas ni pagos.
- El resumen muestra saldos iniciales separados del presupuesto y permite descargar el respaldo JSON de una propiedad propia. No se incluye ninguna credencial.

## Pruebas reproducibles

Desde la raíz del sitio:

```
node_modules/.bin/esbuild lib/preservation.test.ts --bundle --platform=node --format=esm --outfile=/private/tmp/rehab-preservation-test.mjs
node /private/tmp/rehab-preservation-test.mjs
node_modules/.bin/esbuild lib/model.test.ts --bundle --platform=node --format=esm --outfile=/private/tmp/rehab-model-test.mjs
node /private/tmp/rehab-model-test.mjs
node_modules/.bin/tsc --noEmit
npm run build
```

La suite utiliza SQLite real en memoria y las migraciones del proyecto. Verifica conservación exacta, conciliación de totales, repetición, aislamiento por usuario, datos ATTOM, ceros/nulos, fallos a mitad de lote, reanudación, restauración controlada y compatibilidad con el lector anterior.

## Reversión y recuperación

Para revertir esta versión de la aplicación, publicar la versión anterior manteniendo las tablas nuevas. Como el backfill no modifica los datos originales, el lector anterior sigue utilizando `properties`; no hace falta restaurar registros ni borrar tablas. Los respaldos quedan disponibles para revisión posterior.

Si en el futuro se necesitara recuperar datos por una edición posterior, primero comparar versión actual y respaldo de la propiedad exacta, guardar copia del estado actual y obtener autorización para sobrescribir esos cambios. Restaurar únicamente con condición de ID, propietario y fecha/versión esperada para no pisar una edición concurrente. La prueba de recuperación se realizó solo con una propiedad ficticia en memoria.

El respaldo de HU-01 es una copia lógica en la misma base, además de la descarga individual disponible. No sustituye una estrategia independiente de recuperación ante pérdida completa de la base. La migración ocurre al abrir la aplicación o antes de editar cada propiedad anterior; no es un proceso global que copie cuentas que todavía no han accedido.
